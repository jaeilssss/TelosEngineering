Telos V2 · 이해를 위한 한 장 정리

Telos는 코드를 만드는 도구보다
“끝났는지 판정하는 진행 관리자”에 가깝다

프로젝트마다 다른 테스트 방법은 설정 파일에 맡기고, Telos 엔진은 SPEC 확정 → 실행 → 검증 → 판정 → 재시도 흐름만 관리한다.

현재 판단: 방향과 구현 모두 맞음 · 최종 Eval 진행 중
정체성전체 흐름스킬파일 구조무엇이 바뀌었나잘 수정했나최종 답

먼저, 한 문장으로 이해하기

Telos의 역할

“무엇을 만들지 계약하고, 정해진 검증을 거쳐, 근거가 있을 때만 완료라고 말하게 한다.”

전체 동작 흐름

사용자는 목표를 말합니다. Telos는 목표를 SPEC으로 고정하고, 구현이 끝난 뒤 프로젝트가 정한 검증과 독립적인 Eval을 통과해야 완료로 기록합니다.

1

사용자 목표

무엇을 왜 바꿀지 말한다.

2

$spec

모호한 부분을 질문하고 계약으로 만든다.

3

Feature SPEC

완료 기준과 범위를 frozen 상태로 고정한다.

4

$run

구현과 iteration 상태를 관리한다.

5

verify

project.yml에 기록된 명령을 실행한다.

6

$eval

AC와 실제 근거를 비교한다.

7

판정

approved / rejected / uncertain / blocked로 기록한다.

엔진과 프로젝트 지식은 이렇게 나뉜다

이번 개편의 핵심입니다. Telos가 특정 언어나 빌드 도구를 추측하지 않게 만들었습니다.

엔진 — 모든 프로젝트에서 동일

Telos 코드와 스킬이 책임지는 흐름입니다.

SPEC 고정iteration종료 조건SPEC hashunblockEval 리포트

지식 — 프로젝트마다 다름

.telos/project.yml에 저장합니다.

modules[].pathsmodules[].verifyrisks[]scopes[]

현재 스킬은 4개

예전의 impl 별칭과 quick 모드는 제거했습니다. 네 스킬의 역할이 겹치지 않도록 나눴습니다.

S

$spec

“정확히 무엇을 완료해야 하나?”를 정하는 인터뷰 담당입니다.

  1. 핵심 용어와 범위를 질문
  2. 테스트 전략과 AC 작성
  3. 모호성 검사
  4. Feature SPEC을 frozen으로 확정
R

$run

실제 작업을 진행하고 반복 횟수와 상태를 관리합니다.

  1. 명시한 slug로 run 시작
  2. 하네스가 구현 능력 선택
  3. Eval 결과 기록
  4. rejected만 자동 retry
E

$eval

구현 의도가 아니라 증거를 보고 완료 여부를 판단합니다.

  1. 기계 검증 먼저 실행
  2. AC별 반례 확인
  3. approved/rejected/uncertain 판정
  4. Markdown 리포트 기록
V

$review

반복된 거절 이력을 읽고 다음 사고를 막을 방법만 제안합니다.

  1. 기간별 history 조회
  2. 비슷한 실패 근거 묶기
  3. 테스트·lint·risk 순서로 제안
  4. 파일은 직접 수정하지 않음
중요: Telos가 설치된 스킬을 검색해 점수로 고르는 기능은 삭제됐습니다. 지금의 Telos는 “도구 추천기”가 아니라 “계약과 완료 판정 루프 관리자”입니다.

파일은 어디에 저장되나

.telos/                              # 팀과 공유
├── project.yml                       # 모듈·검증·위험·스코프
├── active                            # 현재 선택한 SPEC slug, gitignore
├── specs/
│   ├── payment-flow/SPEC.md            # 기능 계약
│   └── search-v2/SPEC.md
├── runs/payment-flow.json             # 로컬 상태, gitignore
└── evals/payment-flow/1.md            # 로컬 판정 기록, gitignore

실제로 한 번 돌리면

1

SPEC을 만든다

$spec 결제 재시도 개선 → .telos/specs/payment-retry/SPEC.md

2

run을 시작한다

telos run start --spec payment-retry → 상태 파일과 .telos/active 생성

3

코드를 고친다

훅은 파일 확장자가 아니라 project.yml의 paths를 보고 해당 변경인지 판단합니다.

4

Eval이 정해진 검증을 한 번 실행한다

telos verify --changed가 변경 모듈의 verify와 matching risk를 순서대로 실행하고 작업 트리 지문을 저장합니다.

5

Eval한다

scope가 붙은 AC는 scope별 Evidence가 없으면 승인할 수 없습니다.

6

결과를 남긴다

통과는 complete, 실패는 retry, 사용자 판단이 필요하면 blocked 후 명시적으로 unblock합니다.

예전과 지금의 차이

예전

  • 루트 SPEC.md 하나
  • 확장자 목록으로 코드 판별
  • 모델이 테스트 명령을 추측
  • Capability를 검색하고 키워드 점수화
  • Codex·Claude 지침을 복붙 관리
  • blocked 상태를 풀 방법 없음
→

지금

  • slug별 여러 Feature SPEC
  • modules[].paths로 대상 판별
  • modules[].verify로 명령 고정
  • 자동 Capability 라우팅 제거
  • 공통 skill 소스에서 두 번들 빌드
  • hash 감지·unblock·Eval 리포트 추가

그래서, 잘 수정한 게 맞나?

결론부터 말하면 구조적 방향이 맞고, 이전 점검에서 발견한 핵심 빈틈도 이번 hardening 작업에서 보완했습니다.

수정 완료

untracked 파일도 변경 경로에 포함

tracked diff와 Git의 untracked·non-ignored 목록을 합쳐 새 파일만 있는 작업도 모듈 검증에서 빠지지 않습니다.

수정 완료

리포트와 Run 이력 보존

unblock은 iteration을 올리고, 같은 slug의 새 Run은 이전 상태와 Eval 폴더를 같은 archive ID로 이동합니다.

수정 완료

검증 뒤 코드 변경 감지

SPEC hash, iteration, worktree fingerprint가 모두 같아야 Eval 결과를 기록할 수 있습니다. Stage 1 실패도 스냅샷으로 보존됩니다.

수정 완료

로컬 active와 안전한 설치 제거

.telos/active는 Git에서 무시합니다. Codex 플러그인은 ~/.telos/plugins/telos에 설치되고 Telos 소유 파일만 제거합니다.

자주 쓰게 될 CLI

# 변경 모듈의 정해진 검증 실행
telos verify --changed --project-root .

# 설정 생성과 진단
telos init --project-root .
telos doctor --project-root .

# 기능별 실행 시작
telos run start --spec payment-retry --project-root .

# Eval 결과 기록
telos run record --spec payment-retry --status approved --summary "AC 통과"

# rejected 다음 iteration
telos run retry --spec payment-retry

# 사용자 판단으로 blocked 해제
telos run unblock --spec payment-retry --summary "진행 승인"

# 기간별 이력 조회
telos history --since 7d --project-root .

당신이 이해한 방향은 맞습니다

Telos를 더 많은 기능을 가진 만능 에이전트로 만드는 개편이 아닙니다. 반대로 프로젝트별 추측을 걷어내고, 정해진 계약과 검증 근거 없이는 완료라고 말하지 못하게 만드는 범용 엔진으로 좁힌 작업입니다.

현재 구현은 그 방향으로 제대로 이동했고, 이전에 확인한 우선 수정 항목도 코드와 테스트로 보완했습니다. 남은 단계는 최종 Eval과 PR 검토입니다.
